## 1（严重）排雷抓取那一行传了不存在的参数

**位置**：调用 `5674` 行 `load_risk_exclude(force=True)`；函数定义 `6186` 行 `def load_risk_exclude():`

**大白话**：有个函数叫"装载排雷清单"，它不接受任何参数。但每天开盘前的初始化里，调用它的那一行硬塞了一个 `force=True`（意思是"强制重新读一遍"）。程序一旦发现"你给的参数我这儿没有"，会**当场报错**（专业叫 `TypeError`），这个函数的代码一行都不会执行。

**要害**：这一行不在 `try`（异常保护）里面，它一报错，后面三件事全部跳过：
- `load_history()`（加载全部日线）
- `screen_candidates()`（选股，产出候选池）
- `last_init_date`（记录今天已初始化）

**具体例子**：某天早上 9:20 启动策略，排雷数据源（新浪的 ST 名单）刚好抽风没取到。因为没取到，`G.risk_ex_date` 没被设成今天 → 下一轮定时器（30 秒后）**又进这个 `if`** → 又报错 → 循环。结果是：**这一天候选池永远是空的，一笔都不买，日志里只有一串 `traceback`（错误堆栈），没有一句"为什么没买"。** 你会以为是没机会，其实是程序卡死了。

反过来，如果排雷抓取成功，`G.risk_ex_date` 已经被设成今天，下一轮就跳过这个 `if`，自动恢复 —— 所以这个问题只在"排雷抓取失败"时致命，平时只损失开盘后第一轮 30 秒。

**建议修法**：`load_risk_exclude` 增加 `force=False` 参数，`force=True` 时跳过"今天已装载过"的缓存分支直接重读。这样既修掉报错，又真正实现调用处想要的效果（刚抓完的新清单立即生效）。同时给 `_auto_risk_exclude()` 失败路径补一个"今日已尝试"标记，避免每轮重抓 80 秒。

## 2（严重）状态冻结开关被"写盘成功"无条件解除

**位置**：`1326–1329` 行

```python
if G.save_fail_n > 0 or G.state_broken:
    log('[状态] 状态文件落盘已恢复(此前连续失败%d次), 解除交易禁用' % G.save_fail_n)
G.save_fail_n = 0
G.state_broken = False
```

**大白话**：程序里有个总开关 `state_broken`（可以理解成"状态损坏、禁止下单"的红灯）。三处地方会把它点亮，而且都写着"需人工核对"：
- `1458` 行：状态文件里的持仓容器损坏（比如被写成了空值或列表）
- `1481` 行：状态主文件读不出来、备份也读不出来
- `12189` 行：参数指纹（参数校验码）与样本外验证记录不一致

但只要**任何一次写盘成功**，上面这三行就会把红灯**直接关掉**，日志还写着"解除交易禁用"。

**具体例子**：某天状态文件被外部工具写坏，持仓变成空的。策略启动时正确判断"持仓记录全丢了，停止开新仓等人工核对"，还推了手机。**30 秒后**，定时器触发第一次 `save_state()`，把内存里的空持仓写进文件 —— 写盘成功 → 红灯灭。策略认为"一切正常、零持仓"，于是**当天照常开新仓**：真实持仓既不止盈也不止损，还可能在已有持仓的股票上二次建仓，手数也会按"无持仓"放大。

**建议修法**：把红灯拆成两种，用两个标志：
- `save_fail_n`（落盘失败计数）—— 写盘成功可以清零，这是它的本意
- `state_broken`（数据损坏/指纹不一致）—— **只能人工解除**，写盘成功不得清除

## 3（严重）买入费用记两遍，每笔新买入的成本都虚高 5 元

**位置**：`9465` / `9469` 行预填，`11380` 行累加

**大白话**：买入发单时，程序先在持仓记录里"预填"一笔费用估算（`_init_fee`），因为成交回报还没到，先有个数好算账。等成交回报到了，又把真实费用**加**在这笔预填值上，而且**从头到尾没有任何一处在首笔成交时把这笔预填值清掉**。

**实测证据**（用真实模块跑，不是推演）：

```
一张委托 900 股 @28.02 = 25218 元
[1] 发单预填:      h['fee'] = 5.25
[2] 成交回报 100股 → 本笔 5.03，累计 10.28
    成交回报 100股 → 本笔 0.03，累计 10.31
    成交回报 700股 → 本笔 0.19，累计 10.50
[3] 正解: 券商按委托单只收 佣金5.00 + 过户0.25 = 5.25 元
    实际记账 10.50 → 虚高 5.25 元（100%）
```

**更要紧的是**：V2.6.157 刚加的"只修 0.15% 粗估"判据会**恰好跳过它** —— 因为 10.50 与"成交金额×0.15%"（37.83）差 27.33，远超容差 1.00，被判为"非粗估形态，原样保留"。也就是说**这个虚高会被永久固化**，直到这只票卖出。

**危害**：成本虚高 → "扣费净利为正才卖"的门槛被抬高 → **该卖的时候不卖**。金额越大影响越小，仓位越小影响越大：

| 仓位金额 | 真实费用 | 记账费用 | 成本虚高 | 相当于股价虚高 |
|---|---|---|---|---|
| 3,000 元 | 5.00 | 10.00 | 5.00 | 0.17% |
| 6,000 元 | 5.00 | 10.00 | 5.00 | 0.08% |
| 25,218 元 | 5.25 | 10.50 | 5.25 | 0.02% |

**建议修法**：在 `11380` 行累加之前加一道判断 —— 如果是这只票的**首笔成交**（`was_new` 为真），先把 `h['fee']` 归零，再累加真实费用。这样预填值只在"发单到成交回报"这段窗口内起作用，成交后一律以真实回报为准。对补录路径（本来就是 0）无副作用，对分批加仓（非首笔）不影响。

**位置**：`6186–6381` 行，整个函数只有 4 个提前返回（`6192` `6197` `6203` `6207`），**全在"用缓存"的分支里**；真正读盘装载的那条路走完直接到函数结尾，没有 `return data`。

**建议修法**：函数末尾补 `return data if data else _prev`（把刚装载的、或兜底沿用旧表的结果交回去）。

## 5（中等）止盈三个条件互相打架，自动卖出几乎触发不了

**位置**：`3975–4010` 行 `sell_stall_confirmed`

**大白话**：要自动卖出一只已经赚钱的票，必须**同时**满足三个条件：

1. 今天成交量预估 ≥ 基准量的 **1.9 倍**（`EXPAND_SELL_RATIO 2.0 × SELL_TOL 0.95`）
2. 现价比昨天收盘**涨幅 ≤ 1%**（`STALL_MAX_GAIN_PCT`）
3. 现价**低于近 5 个交易日的最高价**（`STALL_NEWHIGH_DAYS`，且不许创新高）

**要害**：第 1 条要"放量近 2 倍"，第 2 条要"几乎没涨"，第 3 条要"还在近 5 日高点之下"。放量 2 倍通常发生在大涨或大跌当天，与"涨幅≤1%"天然矛盾。**三条同时成立的场景，在 A 股极罕见。**

**具体例子**：你手上的 601595 今天浮盈 +124.55 元，量能没有到 1.9 倍，所以不会卖。002226 也是。从可核对的记录看，**策略至今没有过一笔自动卖出**（今天 002232 那笔是你在手机上手工卖的，这笔已被程序正确识别并入账）。

目前唯一能稳定触发的卖出出口是第 4 条：**持有满 33 个交易日且盈利**（`MAX_HOLD_TRDAYS`）。也就是说一只赚钱的票，可能要拿 33 个交易日才自动卖。

**这一条属于策略行为，不是程序 bug** —— 三个参数是你 2026-10-02 拍板加的"高位放量滞涨才是真派发"。要不要放宽、放宽哪一条，需要你定。可选方向：
- A：把"且"改成"或"（涨幅大时也允许卖）—— 会明显增加卖出频率
- B：只保留"未创新高"，去掉"涨幅≤1%"
- C：把放量倍数从 1.9 降到 1.5
- D：维持现状不改，接受"主要靠 33 天到期卖"

## 6（中等）财务报告期把 20260930 读成 1970 年

**位置**：`7038–7042` 行 `_ts_to_date`

**实测**：

| 输入 | 输出 | 对不对 |
|---|---|---|
| `'20260930'` | `'19700823'` | 错 |
| `20260930`（整数） | `'19700823'` | 错 |
| `'2026-09-30 00:00:00'` | `'20260930'` | 对 |
| `1759161600`（秒时间戳） | `'20250930'` | 对 |

**大白话**：函数本来要处理三种日期写法。遇到"纯 8 位数字"（如 20260930）时，它先转成整数，然后**误以为是"1970 年 1 月 1 日以来的秒数"**，于是算出一个 1970 年 8 月的日期。

**危害**：财务数据里有一个"报告期"字段，用来判断"这份财报是不是太老了"。如果数据源用 8 位数字表示报告期，全部会变成 1970 年 → 程序判定"报告期严重滞后"→ 把这只票剔除 → **候选池可能长期为空，日志还写着"过滤正常"**。

**建议修法**：先判断"是不是 8 位数字且前 4 位在 1990~2100 之间"，是就直接当 `YYYYMMDD` 返回；否则再走时间戳分支。

**需要你确认**：这条要不要修，取决于你们广发 QMT 的财务接口到底返回哪种格式。稳妥做法是修 —— 修了不影响时间戳格式，只是多一个分支。

## 7（中等）情绪模块重启后可能永久"未就绪"

**位置**：`14528` / `14547` / `14552` / `14581` 行

**大白话**：情绪模块启动时会把状态清空，但**特意把"今天已经刷新过了"这张小纸条留下来**，同时把"数据已就绪"的开关关掉。而负责刷新情绪的入口，第一句就是"如果今天已经刷新过，直接返回"。

于是：**开关关着，但没有人会再去打开它。** 而 V2.6.151 起，"情绪未就绪"= 一律不许买。

**具体例子**：上午 10:05 情绪已算好、买了 2 只。10:30 你改了参数保存，QMT 重载代码 → 初始化 → 就绪开关关掉、但"今天已刷新"的纸条还在 → 此后每一轮都直接返回 → **当天剩下的买入计划全部作废**，日志只有一句"情绪数据未就绪"，看不出是重启导致的。

**需要你确认**：这一条是否成立，取决于 QMT"重载代码"是**重新执行整个模块**（那么状态字典会被重建为空，纸条不存在，本问题不触发）还是**只重跑 `init()`**（那么纸条保留，问题成立）。你在 QMT 里点"停止"再"启动"时，如果日志里能看到和第一次启动一模一样的横幅，说明模块被重建了。

**建议修法**（无论哪种情况都更安全）：保留下来的"今日已刷新"标记，若同时发现"信号内容为空"，就一并清掉，让刷新重新跑一次。

## 8（中等）情绪两条取数通道的"涨停"定义差 5～10 倍

**位置**：`13652` 行 `_lu_th` 返回 `0.049`（4.9%）；主通道用宿主算好的涨停标记（主板 10%、双创 20%、北交所 30%、ST 5%）

**大白话**：情绪模块有两条路取数。主路（从内存里的日线聚合）用"真涨停"；备用路（直接打行情接口）把**涨幅超过 4.9% 一律算涨停**。同样是"涨停家数占比"，两条路的数字能差 5~10 倍。

**具体例子**：某天真实涨停 60 只，但涨幅超过 4.9% 的有 700 只。走主路，情绪值是 -0.3（中性，可以买）；走备用路，情绪值可能到 +2.1，直接触发"狂热闸门"（`SENT_EVT_FRENZY_LIMITUP = 2.0`）→ 当天禁止开新仓。**同一天、同一份行情，走哪条路决定你今天能不能买。**

注释里说这是"宁可多计不可漏计，方向偏保守"。但只在**亢奋侧**保守；在**恐慌侧**反而放松 —— 情绪值被抬高后，"跌破 -1.5 就收紧买入"这道闸门更难触发。

**建议修法**：备用路也按板块给门槛（主板 9.8%、双创 19.5%、北交所 29.5%，取不到板块信息时用 9.8%）。这样两条路口径一致，且都比真涨停略宽，保持"宁可多计"。

## 9（轻微）委托号登记表按股票只存一条，买卖互相覆盖

**位置**：`5071` 行 `d[code] = {'side': side, 'id': oid, ...}`

**大白话**：程序要记住"这只票最近一笔委托的编号"，用来撤单时精确匹配。但它**按股票代码只留一条**。同一只票先有买单、后有卖单，买单的记录就被卖单覆盖了。
