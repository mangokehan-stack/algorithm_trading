## 三、提前排雷功能（全新上线）

### 3.1 为什么要做

原有风控只在**选股那一刻**看财务/ST，缺三块：

- **临近解禁**：限售股一解禁，大股东就在高位砸盘，你刚买进去就挨跌
- **大股东高位减持**：公告一出，股价阴跌，策略还在加仓
- **被监管立案**：一旦公告，连续跌停，缩量低吸正好接刀

### 3.2 工具：`download_risk_exclude.py`

纯标准库、零依赖，可直接拷到 QMT 机器上跑：

```
python download_risk_exclude.py                    # 默认 45 天窗口, 抓五类风险
python download_risk_exclude.py --days 45 --out zt_shrink_risk_exclude.json
python download_risk_exclude.py --account 8973786  # 多账号: 生成带账号后缀的清单
python download_risk_exclude.py --skip-ann         # 跳过公告源(网络差时提速)
python download_risk_exclude.py --self-test        # 离线自检, 不联网
```

**五个数据源（均已实测可用）**

| 类别 | 接口 | 判据 |
|---|---|---|
| ST / 退市风险 | 公告简称识别（`push2` 行情接口在本机被限流，已绕开） | 简称含 `ST` / `*ST` / `退` |
| 临近解禁 | `RPT_LIFT_STAGE` | 解禁日在 45 天窗口内 |
| 大股东减持 | `RPT_SHARE_HOLDER_INCREASE` | 且 `CHANGE_NUM_SYMBOL < 0`（只认减持，增持不排） |
| 业绩预亏 | `RPT_PUBLIC_OP_NEWPREDICT`，`code=004` | 预亏 / 预减 / 首亏 / 续亏 |
| 监管立案处罚 | `np-anotice-stock` 公告关键词 | 立案 / 处罚 / 警示函 / 监管函 |

**退出码**：`0` 成功；`2` 参数错误；`3` 全部数据源失败。  
**安全设计**：全源失败时**不覆盖已有文件**（防止"生成了一份空清单"造成虚假安全感）。

**实测输出**：617 只命中（公告 22 / 减持 302 / 解禁 237 / 预亏 25 / ST 53）。

### 3.3 策略侧装载与拦截

新增 4 个函数：`risk_exclude_path()` → `_risk_exclude_candidates()` → `load_risk_exclude()` → `risk_excluded(s)`

- **每日只装载一次**（`G.risk_ex_date` 锁定），避免每轮读盘
- **结构校验**：`schema` / `stocks` 字段必须对得上，非法 JSON 或结构不符 → 安全跳过并告警，**不崩策略**
- **单条坏数据跳过**：某只股票记录格式错，只丢这一条，其余照用
- **清单过期仍拦截**（偏紧不放松）：超过 `RISK_EXCLUDE_MAX_AGE_DAYS = 10` 天 → 强提醒但仍按旧清单拦截
- **开关**：`RISK_EXCLUDE_ON = True`，置 False 可一键关闭

**双重拦截**（与选股层形成夹击）

1. **选股层** `excluded()` 返回原因 → 该股进不了候选池
2. **发单前** `buy_stock()` 与 `pyramid_add()` 各插一道 → 即使候选池是旧的（比如清单在盘中更新了），发单前仍会被挡

**只拦新增买入**：卖出、止盈、持仓管理、移交人工处理**完全不受影响**——不违反"坚决不止损"铁律。

> **为什么不拦卖**：排雷的目的是"不买进去"，不是"割肉出局"。已经持有的票，一律交给原有止盈逻辑，绝不因为"它被立案了"就砍仓。

### 3.4 部署步骤

1. 把 `download_risk_exclude.py` 拷到 QMT 策略目录（与母版同目录）
2. 首次运行：`python download_risk_exclude.py`，生成 `zt_shrink_risk_exclude.json`
3. 策略启动时会自动装载，日志出现 `[排雷] 清单已装载: N 只, 生成时间 ...`
4. 建议每个交易日 08:50 定时跑一次（Windows 任务计划）

## 四、自查发现的两个额外缺陷（本轮顺手修掉）

### 4.1 排雷清单"装载失败也锁定当日"（严重）

- **现象**：先启动策略、后跑工具 → 策略当天认为"清单已经处理过了"，但实际读到的是空清单 → **整天不拦截任何风险股**
- **根因**：把"装载动作执行过"当成"装载成功"
- **修复**：只有真正读到**非空**清单才置 `G.risk_ex_date = G.today`；空清单不锁定，并加 **60 秒节流重试**

### 4.2 工具 `--self-test` 污染生产清单（危险）

- **现象**：跑一次自检，5 只样例票（`000001.SZ` / `600000.SH` / `000002.SZ` / `600519.SH` / `002142.SZ`）就被写进了真实清单 `zt_shrink_risk_exclude.json` → 策略当天会**拒买这 5 只正常股票**，而且清单文件看起来"生成正常"，极难排查
- **根因**：自检直接沿用了生产文件名
- **修复**：自检固定写 `zt_shrink_risk_exclude_selftest.json`；策略侧 `_risk_exclude_candidates()` 是按"精确主文件名 + 账号后缀"构造的，不会误读；已删除被污染的文件

### 8.1 情绪降级即锁日 → 全天中性（P1，已实测复现）

**哪里不对**

`_sent_apply_rows` 在函数**入口**就写死了"今天已经取过数了"：

四个降级分支直接 `return`，但标记已经写死了。下一轮 `sent_daily_refresh` 读到"今天已刷新"，直接 `return`，**当天不会再试第二次**。

**具体例子**

- 日志只有一行"降级中性"，之后完全静默，**看不出是"没数据"还是"数据正常且中性"**

**怎么改**

### 8.2 参数指纹含 VERSION → verified_fp 比对永久失效（P1）

**哪里不对**

`param_fingerprint()` 把 `VERSION` 也算进指纹（V2.6.70 引入，为覆盖"不改参数只改代码"的情形）。副作用是**每次升版指纹必变**。

**具体例子**

| 版本 | 参数指纹 | 参数是否改动 |
|---|---|---|
| V2.6.83 | `a36ba5ec` | — |
| V2.6.84 | `77b9f089` | **一行没改**（只改日志文案） |

你在状态文件 `verified_fp` 记录 `77b9f089`，下次改个错别字升到 V2.6.85，启动立刻红标：

```
【参数校验·红标】当前参数指纹与最近一次已记录样本外验证的指纹不一致!
```

久而久之要么每次升版都去改状态文件，要么干脆不看红标。**真正危险的场景恰恰是"参数悄悄改了、版本也升了"——那时红标和平时一模一样，区分不出来。**

而且日志那句"同指纹=同一套参数"在升版时是假的：参数相同也会不同指纹。

**怎么改**

拆成两个指纹：

| 指纹 | 内容 | 用途 | 实测（运行时真值） |
|---|---|---|---|
| `param_fingerprint()` | 只含行为参数（`VERSION` 进 `_FP_DENY`，255 个键） | 与 `verified_fp` 比对，只有参数真变才红标 | V2.6.85 与 V2.6.86 **同为 `392cbf3a`** |
| `code_fingerprint()`（新） | 参数 + `VERSION` | 单独一行「[版本指纹]」，提示"代码可能改动" | `8c30a7a2` → `631c0a07` |

启动日志现在长这样（实际客户端输出）：

```
[参数指纹] 392cbf3a | 样本内外验证纪律: 同指纹=同一套参数; ...
[版本指纹] 631c0a07 | 当前版本=V2.6.86; 版本变更表示代码可能改动, 参数指纹不变则参数本身未变
```

> **口径更正（V2.6.86）**：本节早先写的"跨三版恒定 `94d5c464`"是**错的**，已删除。
> 那个数来自开发机 `_verify_fp.py` 的 AST 近似法——它只抓"单目标字面量赋值"，漏掉多目标赋值、表达式赋值、`try` 块内赋值，而母版 `_fp_keys()` 抓的是 `globals()` 里全部 255 个 `UPPER_CASE` 常量，两者口径不同，算出来自然不等。
> 现脚本改为 exec 母版后直接调用 `param_fingerprint()`，复现值与三轮实盘日志**逐字符一致**：V2.6.83=`a36ba5ec`（256 键，含 VERSION）、V2.6.84=`77b9f089`（256 键）、V2.6.85/86=`392cbf3a`（255 键，VERSION 已剔除）。
> 另外，V2.6.83/84 的值当时含 `VERSION`，与新版**本就不可比**，不存在"三版恒定"这回事。

### 8.3 情绪 overrides 无中文释义（P2）

**哪里不对**

```
overrides=BUY_MIN_ELAPSED_MIN=45;SHRINK_BUY_RATIO=0.3
```

全是英文键和裸数字，**没一处说明改了什么、相对原值差多少**。

**它实际做的是**：

| 参数 | 原值 | panic 档 | 实际效果 |
|---|---|---|---|
| `BUY_MIN_ELAPSED_MIN` | 30 | 45 | 买点从 10:00 **推到 10:15** |
| `SHRINK_BUY_RATIO` | 0.36 | 0.30 | 缩量要求收紧 |

**具体例子**

明天开盘沿用今晚算出的 `regime=panic`。买点窗口实际被推后 15 分钟，但启动日志的 `[策略口径]` 打的还是原始参数，**看不出实际在跑 45 分钟版本**。

新增 `_sent_override_note()`，把键译成「原名 旧值->新值(方向)」，信号刷新后多打一行：

未收录的键**原样输出并标注"未收录"**，不隐藏——保证将来新增覆写项时不会静默。

## 九、V2.6.86：一处文档数字更正（代码零改动）

### 起因

客户端 V2.6.85 实跑日志（22:18:36）打印 `[参数指纹] 392cbf3a`，而文件头版本记录里写的是"实测三版恒定 `94d5c464`"。**文件自述与实际输出不一致**，必须查清是哪边错。

### 结论：错在验证脚本，不在策略

`_verify_fp.py` 旧版用 AST 只抓"**单目标字面量赋值**"来近似复算，而母版 `_fp_keys()` 抓的是 `globals()` 里**全部** `UPPER_CASE` 标量/容器。前者漏掉三类赋值：

|---|---|
| 多目标赋值 | `A = B = 100` |
| 表达式赋值 | `BUY_TOL = SHRINK_BUY * 0.5` |
| `try` / `if` 块内赋值 | `try: HAS_XT = True except: HAS_XT = False` |

漏了键，哈希自然不同。旧版算出 `94d5c464`，运行时真值是 `392cbf3a`。

### 改成同口径后，四个版本逐个对上

`_verify_fp.py` 现改为 exec 母版源码后**直接调用** `param_fingerprint()` / `code_fingerprint()`，与 QMT 同一算法、同一 `globals()`：

| 版本 | 参数键数 | 参数指纹 | 版本指纹 | 与实盘日志比对 |

| V2.6.83 | 256（含 VERSION） | `a36ba5ec` | 无此函数 | ✅ 与 21:57 日志一致 |
| V2.6.84 | 256（含 VERSION） | `77b9f089` | 无此函数 | ✅ 与 22:06 日志一致 |
